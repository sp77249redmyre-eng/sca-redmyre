## 🔴 1. quotes.html — 투표 RULES 변경 (안전 관련, 최우선)

**Part2.md 현재 기술 내용 (11번 항목):** `{ approvalsRequired:5, declinesToAutoDecline:4, holdsToAutoHold:3 }` + "2026-05-12 기준 Interim Fix 적용 중 / 전체 Tie 로직 Fix는 추후 적용 예정" → **이 내용은 이제 과거형입니다. Fix가 이미 적용되어 라이브 중입니다.**

**현재 라이브 코드 (quotes.html 확인):**
```javascript
const RULES = { approvalsRequired: 5, declinesToAutoDecline: 5, holdsToAutoHold: 4 };
const TOTAL_VOTERS = 8;

function calculateResult({ approvals, declines, holds, hasTie = false, totalVoted = 0 }) {
  if (approvals >= RULES.approvalsRequired)     return 'approved';
  if (declines  >= RULES.declinesToAutoDecline) return 'declined';
  if (holds     >= RULES.holdsToAutoHold)       return 'hold';
  if (hasTie    && approvals > 0)               return 'hold';
  if (totalVoted >= TOTAL_VOTERS)               return 'hold';
  return 'pending';
}
```

**변경 요약:**
- `declinesToAutoDecline`: 4 → **5** (거절도 승인과 동일하게 5표 필요)
- `holdsToAutoHold`: 3 → **4**
- Tie 처리: "Interim Fix" 상태 아님 — `hasTie && approvals > 0` → hold로 확정 로직이 정식 반영됨
- `TOTAL_VOTERS=8` 전원 투표 완료 시에도 미결이면 자동 hold
- 페이지 로드 시 16개 케이스 내장 self-test (`validateCalculateResult()`) 콘솔 자동 실행 — 11개였던 이전 기록보다 늘어남

**guide-committee.html은 이미 최신 반영됨** (grep 확인: "✅ 5+ Approve | ❌ 5+ Decline | ⏸ 4+ Hold" 문구 존재, 최종 수정 2026-09-02). 즉 **입주자용 가이드는 맞고, Master Manual(Part1/2/4)의 서술만 뒤처져 있는 상태**입니다.

**Part1.md·Part4.md에도 동일한 `{5,4,3}` 기준이 인용된 곳이 있다면 함께 `{5,5,4}`로 교정 필요.**

## 🔴 2. building.html — 접근 권한 admin 전용으로 변경

**Part2.md 현재 기술 내용:** "접근 가능 Role: 전체 (admin/committee/observer/owner/tenant)"

**현재 라이브 코드 (`layout.js` PAGE_CONFIG):**
```javascript
'building': { title: 'Overview', allowedRoles: ['admin'] },
```

**의미:** Committee/Observer/Owner/Tenant가 `building.html`(Overview)에 접근하면 `checkPageAccess()`에 의해 **`/pages/announcements.html`로 강제 리다이렉트**됩니다 (아래 3번 항목 참고 — 리다이렉트 대상도 바뀜). 사이드바에서도 해당 role들에게는 "Overview" 메뉴가 아예 숨겨집니다.

→ 만약 Committee 등에게서 "Overview 페이지가 안 보인다/리다이렉트된다"는 문의가 오면 **버그가 아니라 의도된 현재 사양**입니다.

Part1.md의 role별 접근 매트릭스, Part2.md `building.html` 섹션의 Role 표를 이 기준으로 수정 필요.

## 🟡 3. layout.js — 그 외 변경사항 (Part3.md Section 1 대상)

Part3.md는 layout.js를 "400줄, PAGE_CONFIG 17개 항목"으로 기술하지만, 현재는 **406줄, PAGE_CONFIG 19개 항목**입니다.

**PAGE_CONFIG 현재 전체 (변경분만 표시):**
```javascript
const PAGE_CONFIG = {
  'building':        { title: 'Overview',             allowedRoles: ['admin'] },        // ← null에서 변경
  'service-reports': { title: 'Service Reports',       allowedRoles: null },              // ← 신규 항목
  'documents':       { title: 'Building Documents',    allowedRoles: ['admin','committee','observer','owner'] }, // ← 신규 항목
  // ...기존 announcements/parking/complaints/hvac/emergency/works/cost-dashboard/history/quotes/reports/occupants/signboard/users/system/guide-resident 는 동일
  'guide-committee': { title: 'Committee Guide',       allowedRoles: ['admin', 'committee', 'observer'] }, // 동일
};
```

**추가로 확인된 변경점 3가지:**

1. **`import '/js/my-profile.js';`** — 라인 2에 신규 추가. 모든 페이지가 layout.js를 통해 my-profile.js 모듈을 자동으로 로드하게 됨 (아래 4번 참고).
2. **`checkPageAccess()`의 리다이렉트 대상 변경**: `/pages/building.html` → **`/pages/announcements.html`**. building.html 자체가 admin 전용이 되었으므로, 권한 없는 페이지 접근 시 예전처럼 building.html로 보내면 무한 리다이렉트 루프가 생기기 때문으로 추정됨(합리적 수정).
3. **`initLayout()` 마지막에 `window.__bmsCtx = ctx;` 추가** — `{ supabase, user, profile, role, name }`을 전역으로 노출. my-profile.js가 이 값을 읽어서 사용.
4. **`applyRoleMenuControl()`의 하드코딩 fallback 리스트** — admin 리스트 및 committee/observer/owner 리스트 각각에 `'service-reports'`가 추가됨. `'documents'`는 tenant를 제외한 나머지(admin/committee/observer/owner) fallback 리스트에 추가됨.

## 🟢 4. `/js/my-profile.js` — 신규 파일 (806줄, Part3.md에 없음)

**전역 등록:** `window.openMyProfile()` / `window.closeMyProfile()` — layout.js가 자동 import하므로 모든 페이지에서 호출 가능 (사이드바/탑바의 "내 프로필" 버튼 등에서 트리거되는 것으로 추정).

**핵심 동작:**
- `window.__bmsCtx`(layout.js가 노출)에서 현재 유저 정보를 읽음
- `loadAndRender()` — `occupants.primary_email` / `business_email`을 현재 로그인 이메일과 매칭해서 본인이 소유/거주 중인 유닛(들)을 찾음
- **admin/observer** → `renderSimpleProfile()` (이름/이메일 정도의 최소 정보만)
- **owner/tenant/committee** → `renderFullProfile()`:
  - 매칭된 각 유닛에 대해 OWNER/TENANT/STAFF 역할을 자동 판정해서 표시
  - 다중 유닛 소유자는 체크박스로 선택 후 **사업자 정보(business_name 등) 일괄 동기화** 가능
  - 차량 번호판 관리 (`sync_vehicles` RPC 호출 — occupants.html과 동일한 RPC 재사용)
  - 비밀번호 변경 (`auth.signInWithPassword`로 현재 비번 재확인 후 `auth.updateUser`)

**DB/RPC 사용:** `occupants` 테이블 (읽기/쓰기), `sync_vehicles()` RPC (재사용, 신규 아님)

**Part3.md에 "JS 모듈 5번째"로 신규 섹션 추가 필요.** (기존 auth.js/common.js/audit.js/layout.js 4개 체제에서 5개로)

## 🟢 5. `/api/admin-edit-profile.js` — 신규 API (353줄, Part3.md에 없음)

**8번째 Vercel API** (Part3.md는 현재 7개: check-email, complete-setup, admin-set-password, delete-user, send-invite, send-push, admin-change-email 까지만 기술).

**인증:** Bearer 토큰 필수 + `profiles.role === 'admin'` 검증 (2단계: 먼저 anon key+토큰으로 유저 확인용 클라이언트, 그 다음 Service Role 클라이언트로 실제 변경 — `admin-set-password.js`와 동일 패턴)

**용도:** `users.html`에서 Admin이 유저의 **이름/유닛/이메일**을 한 번에 편집할 때 사용. `admin-change-email.js`(이메일만 변경)보다 범위가 넓은 통합 편집 API로 보임.

**동작 요약:**
- 자기 자신 이메일 변경은 차단
- 이메일 형식 검증 + 중복 체크
- Auth 이메일 변경(`email_confirm: true`) + `profiles` 업데이트, 부분 실패 시 롤백 시도
- 이메일 또는 이름 변경 시 → `occupants.primary_email`/`business_email`을 콤마/세미콜론 분리 후 동기화 (dedup 포함)
- 유닛 변경 시 → 기존 유닛 occupants 행에서 이메일 제거, 새 유닛 occupants 행에 추가 (role이 tenant면 `business_email`, 아니면 `primary_email` 타겟)
- 에러는 `audit_logs`에 `action: 'api_error'`로 기록 (로컬 `logError()` 헬퍼)

**users.html 쪽 연동 확인됨:** "admin-edit-profile API 호출 (Auth + profiles + occupants 통합 동기화)" 주석과 함께 실제 호출 존재.

**Part3.md 반영 필요 사항:**
- Section 2 "6개 API" → **9개 API**로 (admin-change-email 포함 시 8개였던 것에 +1)
- `users.html` 섹션의 "연결되는 파일" 목록에 `/api/admin-edit-profile.js` 추가
- Section 2 요약 비교표에 행 추가

## 🟡 6. `documents.html` — 신규 페이지 (830줄, Part2.md에 없음)

**URL:** `/documents` (추정, rewrites 확인 필요) · **접근 권한 (layout.js 기준):** admin/committee/observer/owner (tenant 제외)

**용도:** 2-패널 구조의 건물 문서 보관함.

**① SCM Documents 패널 (좌측)**
- `scm_meetings` 테이블 (회의: title, meeting_date) + `scm_documents` 테이블 (첨부파일)
- 연도 선택 → 월별 그리드(month-grid)로 회의 존재 여부 표시
- Storage 버킷: `scm-documents`

**② Building Documents 패널 (우측)**
- `building_categories` 테이블 (카테고리: name/icon/color/position, Admin이 CRUD) + `building_documents` 테이블 (첨부파일)
- 카테고리 카드 클릭 → 해당 카테고리 파일 목록
- Storage 버킷: `building-documents`

**공통 파일 처리 함수:** 업로드(`upload`) / Signed URL 생성(`createSignedUrl`, 1시간) / 다운로드(`download`) / 삭제(Storage + DB 동시) — 기존 quotes/works와 동일한 4중 방어망 패턴은 아니고 role 기반 Storage RLS로 추정(코드에서 명시적 role 분기문은 못 찾음 — RLS 정책 직접 확인 필요).

**Part2.md 그룹 C(입주자 기능) 또는 별도 그룹에 신규 항목으로 추가 필요. Part1.md에는 `scm_meetings`/`scm_documents`/`building_categories`/`building_documents` 4개 테이블과 2개 Storage 버킷 명세 추가 필요 (테이블 스키마는 이번 조사에서 컬럼 레벨까지는 확인 안 함 — 필요시 추가 조사).**
